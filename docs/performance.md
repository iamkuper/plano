# Производительность: замер на большой базе

Замер повторяется командой `pnpm --filter @plano/api bench` (база `kanban_bench`, создаётся и заполняется сама за ~30 секунд; `BENCH_RESET=1` — заполнить заново, `BENCH_SMALL=1` — маленький набор для проверки скрипта). Отчёт печатается в консоль и пишется в `apps/api/bench/last-run.md`. Код: `apps/api/bench/`.

## Что в базе

Один крупный клиент и 30 небольших, чтобы индексы работали на общей таблице:

| | |
|---|---|
| Размер базы | 152 МБ |
| Карточки | 43 тыс. (у крупного клиента 25 тыс. в 150 проектах: один проект на 3000, десять по 800, остальные по 100) |
| Комментарии / подзадачи / история | 36 тыс. / 49 тыс. / 130 тыс. |
| Журнал действий / учёт времени | 35 тыс. / 17 тыс. |
| Сотрудники у крупного клиента | 60; «администратор» исполнитель у ~2000 карточек, «сотрудник» у ~500 |

Замер идёт через HTTP внутри одного процесса (сервер и клиент делят процесс), локальный Postgres без сетевой задержки, запросы с `Accept-Encoding: gzip`, кэш проверки пользователя включён. Абсолютные числа на проде будут иными (сеть до базы, другие ядра), важны соотношения.

## Выводы

1. **Самая дорогая вещь — счётчик «срочно» в левом меню.** `useUrgentCount` на каждой загрузке любой страницы запрашивает все карточки исполнителя (2,4 МБ, ~400 мс, 70% — работа Node) и ради этого считает число. Это половина времени открытия главной. Нужен лёгкий запрос `count` (`/cards/urgent-count`), ~5 мс и пара байт.
2. **«Задачи команды» без фильтра отдают все карточки активных проектов: 29 МБ и 4,5 с.** На странице «Задачи команды» нужны пагинация или лимит и фильтры на сервере.
3. **Основное время — не база, а Prisma.** На вложенных `include` (исполнители, метки, подзадачи, проект) Node тратит в 2–3 раза больше времени, чем Postgres. Лечение: одним SQL с `json_agg` или более лёгкий ответ плитки (без описания, подзадач и т. п.), загрузка длинных колонок частями.
4. **`_count` комментариев и вложений читает всю таблицу.** В плане видно `Seq Scan on "Comment"` (36 тыс. строк) в каждом запросе доски и команды: Prisma считает счётчики по всей таблице, а не по выбранным карточкам. Время растёт с размером базы всех клиентов. Исправление: счётчики отдельным `groupBy` по нужным `cardId` (индекс `(cardId, createdAt)` есть) или счётчики в самой карточке.
5. **Поиск по карточкам — полный перебор.** 90–144 мс на 43 тыс. карточек и растёт линейно (`ILIKE` по названию и описанию). Лечится индексом `pg_trgm` (GIN) или ограничением выдачи; номер `TSK-N` можно искать точно по `number`.
6. **Список проектов:** 30 мс, из них 14 в SQL на подсчёт карточек по колонкам. Допустимо, но при росте числа проектов лучше хранить счётчики.
7. **Отчёт по времени отдаёт до 5000 записей (1,8 МБ):** нужен лимит по умолчанию или серверная агрегация.
8. **Сортировка больших выборок уходит на диск** (`external merge Disk: 6608kB` в «всей команде»): при больших выдачах увеличить `work_mem` или вообще не отдавать столько.
9. **Малые запросы в порядке:** `me`, `settings`, `labels`, `cards/:id`, `audit`, запись карточек — 3–26 мс.
10. **gzip** сжимает в 8–9 раз (2,4 МБ → 283 КБ на синтетике), но стоит 40–70 мс CPU на тяжёлых ответах. Уменьшать нужно сам ответ.

## Первый раунд исправлений

Сделано по этому отчёту; замер повторён на той же базе.

| Запрос | было, мс | стало, мс | что изменено |
|---|---:|---:|---|
| Открытие главной (8 запросов разом) | 425 | **51** | счётчик «срочно» и сводка по этапам стали лёгкими запросами |
| Счётчик «срочно» в меню | 416 (2,4 МБ) | **12** (несколько байт) | `GET /cards/urgent-count`: один `COUNT` в SQL вместо загрузки карточек |
| Сводка по этапам для главной | 4506 (29 МБ) | **34** | `GET /team-board/summary` |
| «Задачи команды», первая загрузка | 4506 (29 МБ) | **189** (1,1 МБ) | порции по 200 карточек на этап и кнопка «Показать ещё» (`?limit=200`) |
| Моя лента (`team-board?assigneeId=админ`, 2000 карточек) | 416 | 258 | карточки собираются по плоским запросам |
| Доска, 100 карточек | 41 | 23 | то же |
| Доска, 800 карточек | 144 | 86 | то же |
| Доска, 3000 карточек | 475 | 305 | то же |
| Поиск по ключу `TSK-1500` | 90 | 10 | trigram-индексы + точный поиск по номеру |
| Поиск редкого слова | не меряли (полный перебор, ~90 мс) | **5** | индексы `pg_trgm` (GIN) на название и описание |
| Тяжёлый запрос при 10–30 параллельных | 122–131 | 96–102 | меньше работы в Node |

Что именно сделано:

- `GET /cards/urgent-count`, `GET /team-board/summary`, пагинация `GET /team-board?limit=&stage=&offset=`, лимит 1–500.
- Плитки карточек собираются вручную (`boards/card-tiles.ts`): плоские запросы вместо вложенных `include`, счётчики комментариев и вложений отдельным `groupBy` по нужным карточкам (`boards/card-counts.ts`) вместо `_count` по всей таблице.
- Индексы (миграция `20261022000000_performance_indexes`): `pg_trgm` GIN на `Card.title` и `Card.description`, `CardAssignee(userId)`, `TimeEntry(date)`.
- Кэш проверки пользователя и gzip (предыдущий этап).

## Что осталось

- **Описание в плитке.** Доска на 3000 карточек всё ещё 4 МБ (в синтетике ~35% — описания). Нужно решение: отдавать в плитке только начало описания (например, 300 символов), тогда фильтр по тексту на доске не найдёт слова дальше; либо искать по тексту на сервере.
- **Общий `GET /team-board` без `limit`** остаётся прежним (2,4 с, 29 МБ), им пользуются только внешние вызовы; веб ходит с `limit`.
- **Моя лента на главной** (`team-board?assigneeId=`) по-прежнему загружает все открытые задачи человека (258 мс при 2000): достаточно первых 200 по сроку плюс счётчики.
- **Отчёт по времени** (310 мс, 1,8 МБ на 5000 записей): сделать агрегацию на сервере или плоскую выдачу без повторяющихся вложенных объектов.
- **Список проектов и уведомления** (~30 мс): счётчики карточек по колонкам считаются при каждом запросе; можно хранить.
- **Клиент:** точечные обновления доски по событиям и кэш запросов, чтобы страницы реже перезагружались.
